# 黑马点评微服务改造方案

> 项目：hm-dianping  
> 基础版本：Spring Boot 2.3.12.RELEASE + MyBatis-Plus 3.4.3  
> 目标架构：Spring Cloud Alibaba 微服务架构  
> 文档用途：作为 `hm-dianping` 单体项目向微服务架构迁移的实施方案、开发任务依据和 AI 协作依据。

---

## 1. 改造目标

本次改造不是简单地将原单体项目拆成多个 Spring Boot 模块，而是将现有黑马点评教学型单体项目演进为具备以下能力的微服务项目：

1. 按业务领域划分服务边界。
2. 服务之间通过 Feign 通信，禁止跨服务直接访问数据库。
3. 每个业务服务拥有明确的数据所有权。
4. 使用 Nacos 完成服务注册与配置管理。
5. 使用 Gateway 作为统一流量入口，集中完成鉴权、路由和用户身份透传。
6. 使用 Redis 支撑缓存、分布式锁和秒杀前置校验。
7. 使用 RabbitMQ 实现秒杀订单异步落库。
8. 使用幂等机制保证消息消费和写操作的最终一致性。
9. 使用 Canal + MQ 支撑需要较高一致性的缓存同步场景。
10. 使用 Sentinel 提供限流和熔断能力。
11. 修复原项目中已经发现的安全、并发、缓存和资源清理问题。
12. 保留原项目核心业务能力，避免为了微服务化而无意义重写业务。

---

## 2. 原项目现状

原项目为 Spring Boot 单体应用，主要包含：

- User
- UserInfo
- Follow
- Shop
- ShopType
- Voucher
- SeckillVoucher
- VoucherOrder
- Blog
- BlogComments

原项目所有业务共享：

- 一个 Spring Boot 启动类
- 一个 MySQL 数据库
- 一个 Redis
- 一套 Mapper / Service / Controller
- 一个 RedisConstants
- 一个 UserHolder
- 一套全局配置

当前已知问题包括：

| 问题 | 原因 | 改造方向 |
|---|---|---|
| 服务边界不清晰 | 所有业务位于同一应用 | 按领域拆分服务 |
| Blog 跨域依赖 UserService | 单体中直接注入 IUserService | 改为 Feign |
| 数据库边界不清晰 | 所有服务共享表 | 明确表所有权 |
| 用户身份依赖单体拦截器 | Token 鉴权位于业务服务 | Gateway 统一鉴权 |
| ThreadLocal 未清理 | UserHolder 未 remove | afterCompletion 清理 |
| Redis Key 全局混杂 | 所有业务共用 RedisConstants | 按服务划分 |
| RedisData 重复 | entity 与 utils 中存在重复类 | 合并 |
| 秒杀同步落库 | DB 写入位于主流程 | MQ 异步落库 |
| 秒杀幂等不足 | 依赖业务代码控制 | Redis + DB 唯一索引 |
| 文件上传存在路径穿越风险 | 文件名未充分规范化 | CanonicalPath + 前缀校验 |
| 敏感配置硬编码 | application.yaml 存在明文密码 | Nacos / local 配置 |
| 缓存一致性不足 | 主要依赖业务代码删除缓存 | Canal + MQ 支撑高一致场景 |

# 4. 数据边界

微服务之间禁止直接访问其他服务的数据表。

推荐数据库划分：

```text
user-service
    ↓
hmdp_user
    ├── tb_user
    ├── tb_user_info
    ├── tb_follow
    └── tb_sign

shop-service
    ↓
hmdp_shop
    ├── tb_shop
    └── tb_shop_type

voucher-service
    ↓
hmdp_voucher
    ├── tb_voucher
    ├── tb_seckill_voucher
    └── tb_voucher_order

blog-service
    ↓
hmdp_blog
    ├── tb_blog
    └── tb_blog_comments
```

### 原则

1. 每张业务表只能属于一个服务。
2. 服务只能直接访问自己的数据库。
3. 跨服务数据通过 Feign 或消息事件获取。
4. 禁止为了方便而跨服务 SQL Join。
5. 不向其他服务暴露 Entity，跨服务使用 DTO。
6. 单服务内部事务使用 `@Transactional`。
7. 跨服务一致性不依赖本地 `@Transactional`。

# 6. P1：Gateway 与用户身份体系

## 6.1 原架构

```text
Request
 ↓
RefreshLoginInterceptor
 ↓
LoginInterceptor
 ↓
UserHolder
 ↓
Controller
```

## 6.2 新架构

```text
Client
 ↓
Gateway
 ↓
Token 校验
 ↓
Redis 获取 userId
 ↓
X-User-Id
 ↓
业务服务
 ↓
UserInterceptor
 ↓
UserHolder
 ↓
Controller / Service
```

## 6.3 Gateway 职责

Gateway 统一完成：

- Token 提取。
- Token 校验。
- Redis 查询用户身份。
- `X-User-Id` 请求头透传。
- 路由。
- 后续 Sentinel 限流。

业务服务不再重复执行完整 Token 鉴权。

## 6.4 下游服务

业务服务只需要：

```text
X-User-Id
 ↓
Interceptor
 ↓
UserHolder
```

并且必须：

```java
afterCompletion() {
    UserHolder.removeUser();
}
```

防止线程池复用导致用户串号。

## 6.5 安全要求

内部业务服务不能直接对公网暴露。

如无法通过网络层隔离，则下游服务必须增加请求来源校验，防止绕过 Gateway。

# 11. 秒杀架构改造

## 11.1 原流程

```text
HTTP
 ↓
Redis Lua
 ↓
创建订单
 ↓
MySQL
 ↓
Response
```

## 11.2 新流程

```text
HTTP
 ↓
Gateway
 ↓
voucher-service
 ↓
Redis Lua
 ↓
库存扣减 + 一人一单校验
 ↓
发送 MQ
 ↓
快速返回
```

异步：

```text
RabbitMQ
 ↓
Order Consumer
 ↓
数据库事务
 ↓
voucher_db
```

## 11.3 Lua

Lua 必须保证：

```text
库存是否充足
+
是否已经购买
+
扣减库存
```

在 Redis 中原子完成。

## 11.4 MQ

RabbitMQ：

- Exchange durable。
- Queue durable。
- Publisher Confirm。
- Return 回调。
- Consumer 手动 Ack。
- 失败重试。
- 超过重试次数进入 DLQ。

## 11.5 幂等

至少保证：

```text
Redis SETNX
+
DB 唯一索引
```

或者根据实现选择其中一种作为核心幂等手段。

DB 最终必须使用唯一约束兜底。

# 12. P6：Canal 与缓存一致性

Canal 不作为第一阶段基础设施，而在服务拆分和 MQ 稳定后引入。

目标链路：

```text
MySQL
 ↓
binlog
 ↓
Canal
 ↓
MQ
 ↓
Cache Consumer
 ↓
Redis
```

适用于对缓存一致性要求较高的场景。

基本策略：

```text
普通场景：
DB 更新
 ↓
删除缓存

高一致场景：
DB 更新
 ↓
binlog
 ↓
Canal
 ↓
MQ
 ↓
异步更新/删除缓存
```

禁止为了引入 Canal 而对所有缓存逻辑进行过度复杂化。

# 13. P7：Sentinel

在基础服务稳定后增加 Sentinel。

主要保护：

- Gateway。
- 用户接口。
- 店铺查询。
- 秒杀接口。
- Feign 调用。

重点验证：

```text
QPS 限流
 ↓
超过阈值
 ↓
快速失败 / 降级
```

以及：

```text
服务调用异常
 ↓
熔断
 ↓
避免故障扩散
```

# 14. Common 模块设计

`hmdp-common` 只放真正跨服务共享的内容。

推荐：

```text
hmdp-common/
└── src/main/java/com/hmdp/common/
    ├── dto/
    │   ├── Result
    │   ├── UserDTO
    │   └── ...
    ├── exception/
    ├── constant/
    ├── context/
    │   └── UserContext
    ├── feign/
    │   └── UserFeignClient
    └── utils/
```

禁止将所有业务 Entity、Mapper、Service 实现放入 common。

Common 应该保持轻量，避免形成新的“单体公共模块”。

# 19. 事务设计

## 19.1 单服务事务

允许：

```java
@Transactional
```

例如：

```text
voucher-service
    ↓
voucher_order
    ↓
seckill_voucher
```

这些属于同一个数据库事务边界。

## 19.2 跨服务事务

禁止：

```text
@Transactional
 ↓
Feign A
 ↓
Feign B
```

将跨服务一致性设计为：

```text
MQ
+
幂等
+
重试
+
补偿
```

## 26. 改造原则

1. **先拆边界，再拆代码。**
2. **先建立基础设施，再迁移业务。**
3. **一个服务拥有自己的数据，不跨库。**
4. **跨服务调用只能通过 Feign。**
5. **Gateway 负责统一鉴权，业务服务负责身份上下文。**
6. **单库事务使用本地事务，跨服务一致性使用 MQ + 幂等 + 补偿。**
7. **秒杀先保证 Redis 原子性，再通过 MQ 削峰。**
8. **不要为了使用中间件而使用中间件。**
9. **每完成一个阶段都必须能够运行和验证。**
10. **每个架构决策都应该能够在面试中解释“为什么”。**
